## 1. 先给出准确结论

原始 ai-agent-scaffold 不是一个空壳项目，也不是一个只能返回普通文本的 Agent 示例。它已经是一个能够运行的 Go + Next.js Draw.io Agent 应用，主要能力包括：

- 从 .env 与 YAML 读取中转站、模型、Agent、Workflow、MCP 和 Skill 配置；
- 通过 OpenAI-compatible Chat Completions 调用模型；
- 以 Analyst → Drawer → Reviewer 三个角色顺序生成 Draw.io XML；
- 在单个 LLM Agent 内处理“模型请求工具 → 执行工具 → 把结果交回模型”的最多四轮工具循环；
- 通过 SSE MCP 客户端执行 initialize、tools/list 和 tools/call；
- 提供同步 /chat 与流式 /chat_stream 接口；
- 前端保存多条本地聊天、消息和图纸，并能把当前画布 XML 显式附到下一次请求。

用户已经确认：项目此前使用 .env 中配置的中转站能够正常运行。当前 API Key 是否过期、上游是否限流、某个 MCP 服务是否在线，属于某一时刻的外部环境状态，不能用来否定上述代码能力。

## 4. 启动阶段：YAML 怎样变成可以调用的 Runner

启动入口在 cmd/server/main.go。执行顺序是：

1. 命令行 -env 默认指向 .env，-config 默认指向 configs/application.yaml。
2. loadDotenv 使用 godotenv.Read 读取文件。
3. 如果操作系统已经存在同名环境变量，就保留操作系统值；否则才把 .env 值写入进程环境。
4. LoadApplication 读取端口、LLM 超时、Agent 配置路径等应用配置。
5. bootstrap.Build 读取两份 Agent YAML。
6. Loader 把 YAML 里的环境变量占位符展开成进程环境中的值，并校验 base-url、api-key、模型、Agent 和 Runner 等必填项。
7. Bootstrap 创建内存 Registry、内存 SessionStore、模型 Provider、MCP Router、ToolFactory、SkillFactory 和 Agent Factory。
8. Armory 责任链按 Root → AiAPI → ChatModel/Tools → Agents → Workflows → Runner 的顺序组装每张配置表。
9. 最终用 agentId 把两个应用注册到 AgentRegistry。
10. Gin 注册 HTTP 路由并监听配置端口。

这里有两个容易混淆的 Context：

- 装配期 DynamicContext 保存正在构造的 API、Model、Agent 和 Workflow 对象；
- 单次运行的 vars/scope 保存 analysis_result、draft_diagram 等中间输出。

前者用于“把配置装成对象”，后者用于“一次请求内传数据”。

## 5. 一次真实绘图请求怎样执行

前端的 performSendMessage 是实际发送主流程。以“画一个登录流程图”为例：

1. 页面先把用户输入追加到当前浏览器会话。
2. 如果还没有 backendSessionId，先调用 POST /api/v1/create_session。
3. 页面调用 agentApi.chat，向 POST /api/v1/chat 发送 agentId、userId、sessionId 和 message。
4. HTTP Handler 把 JSON 转成 ChatCommand，交给 ChatService。
5. ChatService 根据 agentId 找到已注册 Runner；没有 sessionId 时创建或复用一个。
6. Runner 触发配置的插件 Hook，然后执行入口 Agent sequential_draw_process。
7. runSequential 为本次请求创建独立 scope，依次调用三个子 Agent。
8. 每个 LLM Agent 都会得到自己的 system instruction 和同一份当前 user message。
9. 子 Agent 配置了 output-key 时，结果会写入 scope，供后续 instruction 占位符替换。
10. 顺序工作流最终返回最后一个子 Agent 的输出。
11. HTTP 把结果包装成 data.content。
12. 前端用字符串特征判断它是否像 Draw.io XML；如果像，就保存到当前本地会话并调用 drawioRef.current.load。

原始数据流是：

    user message
      → Analyst
      → scope["analysis_result"]
      → Drawer 的 {analysis_result}
      → scope["draft_diagram"]
      → Reviewer 的 {draft_diagram}
      → Reviewer 最终 XML
      → Runner 最后一个字符串
      → HTTP data.content
      → localStorage + Draw.io load

注意：Analyzer、Drawer 和 Reviewer 并不是三个独立进程，也不会自由讨论。它们是一个进程内由顺序 Workflow 依次调用的三个角色。

## 6. 原 agent_reviewer 到底输出什么

原始绘图 YAML 写得很清楚：

- agent_drawer 输出 draft_diagram，要求是完整 Draw.io XML；
- agent_reviewer 读取 draft_diagram；
- Reviewer 检查标签、属性、ID、source/target 和布局；
- 发现问题时直接修正；
- 输入完全不像 XML 时，Reviewer 甚至被要求自行重写一份最简合法 XML；
- 最终只能返回以 mxfile 开头、以 /mxfile 结束的裸 XML；
- output-key 是 final_result。

所以，准确说法是：

> 原 Reviewer 的协议输出就是 XML，并且它已经把“判断问题”和“直接修改”放在同一次模型调用中。

原运行时的问题不是“不知道 Reviewer 应该返回 XML”，而是：

- ChatReply.Content 在 Go 中仍然只是 string；
- Runner 没有 XML Parser 去验证实际字符串；
- 提示词是对概率模型的约束，不是类型系统或解析器；
- 程序不知道 Reviewer 发现了哪些问题；
- 程序不知道 Reviewer 是否认为已经通过；
- 没有可记录的 issue 列表；
- 没有由程序管理的修复次数和停止条件；
- 顺序 Workflow 无条件把最后一个字符串当成最终结果。

Day 2 Validator 解决“最终字符串是否满足本项目的确定性 XML 契约”。Day 3 以后解决“业务语义是否满足、问题是什么、是否需要进入受限 Repair”。

## 7. 原项目其实已经有两种循环概念

### 7.1 单 Agent 工具循环

runLLM 最多执行四轮：

    模型
      → 没有 tool_calls：返回文本
      → 有 tool_calls：调用 ToolRouter
      → 把 assistant tool_calls 与 role=tool 结果追加回 messages
      → 再调用模型

这个循环用于让模型取得外部工具结果。达到四轮仍继续请求工具时，运行返回超限错误。

### 7.2 YAML 中的 loop 工作流

配置里确实有 loop_refinement 和 max-iterations: 3，但当前 adapter 对 loop 和 parallel 都调用 runFanOut。runFanOut 只用普通 for 循环把子 Agent 各执行一次并聚合结果：

- loop 没有读取 MaxIterations；
- loop 没有检查 Reviewer 结果后决定是否继续；
- parallel 没有 goroutine，也不是真并发；
- 对外 Runner 选择的是 sequential_draw_process，两个示例 Workflow 并不处理网页绘图请求。

因此“配置里有 loop”与“已经有 Reviewer Repair Loop”是两回事。后续不会复用含义不清的 MaxIterations 来假装完成质量闭环，而会显式定义 max_repairs、候选版本、检查结果和退出状态。

## 8. 模型与中转站链路

虽然类型名叫 EinoProvider 和 EinoChatModel，实际模型请求由项目自己的 OpenAIClient 完成。go.mod 没有 CloudWeGo Eino 依赖。调用步骤是：

1. EinoProvider 校验 base URL 和 API Key；
2. joinURL 拼出 chat completions 地址；
3. OpenAIClient 构造 Bearer Authorization 和 JSON 请求；
4. Generate 解析第一条 choice 的 content 与 tool_calls；
5. Stream 读取 OpenAI-compatible SSE data 行，转成 ChatStreamEvent；
6. 当前端口没有解析和保留 provider usage。

当前 .env 中以下变量均有非空值，但文档不保存其内容：

- APP_ENV；
- SERVER_ADDR；
- OPENAI_BASE_URL；
- OPENAI_API_KEY；
- BAIDU_SEARCH_MCP_BASE_URI；
- BAIDU_SEARCH_MCP_SSE_ENDPOINT。

离线配置检查能够识别配置模型 gpt-5.5、两项 MCP 配置和一组 Skill 配置。用户确认这套中转站配置以前可用。本次复核只验证中转站主机 TCP 当前可达，没有重新断言 Key、模型路由或完整聊天请求当前成功。

## 9. MCP：已经实现了什么，问题在哪里

原项目有完整度较高的 SSE MCP 客户端，不应写成“没有 MCP”。MCPSSEClient 会：

1. 对 SSE 地址建立 GET 长连接；
2. 读取 endpoint 事件，取得 JSON-RPC POST 地址；
3. 发送 initialize；
4. 发送 initialized 通知；
5. 调用 tools/list；
6. 收到模型 tool_calls 后调用 tools/call；
7. 把文本结果交回 LLM 工具循环。

两份 Agent YAML 都配置：

- 百度搜索 MCP，地址来自 .env；
- everything-test，本地固定为 127.0.0.1:3001/sse。

当前真正需要注意的缺口有四个。

第一，启动期 tools/list 只有 10 秒发现窗口。失败后 RegisterAndExpand 不会让整个应用装配失败，而是保留一个以服务名命名的占位 Tool。因此：

- 后端仍可能启动；
- 模型也可能看到 baidu-search 或 everything-test；
- 真正调用时才暴露远端问题；
- “应用已启动”不能证明 MCP 工具可用。

第二，listFailures 保存了发现错误，但没有日志、健康检查或 API 把它显示出来，排错体验较差。

第三，tools/list 解析时只保存 name，没有保存 description 和 inputSchema。发给模型的所有工具都被统一描述为一个可选 query 字符串。服务端若要求多个结构化参数，模型很可能生成不符合真实 Schema 的 arguments。

第四，SkillFactory 能扫描本地 SKILL.md 并生成 SkillTool，ChatModel 也能把它暴露给模型；但 executeToolCalls 只会进入 MCPToolRouter，SkillTool 没有真正的执行器。当前状态应表述为“Skill 可发现但不可执行”。

本次 TCP 快照显示：中转站主机可达；百度 MCP 与本地 everything-test 在检查时未连通。它只描述当前检查时刻，不覆盖用户过去正常运行的模型链路，也没有完成 MCP 协议级鉴权验证。

## 10. Streaming：不是完全没有，而是没有工作流事件

后端已有 POST /api/v1/chat_stream，OpenAIClient 也能处理模型 token SSE。

但要分两种入口：

- 入口 Agent 是普通 LLM 时，Agent.stream 会调用模型 Stream，能逐段输出 token；
- 入口 Agent 是 Workflow 时，Agent.stream 先同步调用 run，三个角色全部完成后才把最终结果一次性写入 Channel。

绘图应用的入口是 sequential Workflow，所以它的 /chat_stream 目前并不会实时告诉前端“Analyst 已开始、Drawer 已完成、Reviewer 正在检查”。另外前端 agentApi 只封装并调用 /chat，没有调用 /chat_stream。

后续所谓“事件级 SSE”是在已有 HTTP 流通道上增加工作流事件、取消和前端消费，而不是从零增加所有 Streaming。

## 11. Session、前端历史与 Memory 的区别

### 11.1 后端 sessionId

当前 SessionStore 是内存 map，键是 userId + agentId。CreateSession 会先查这个键，已存在就直接返回旧 ID。这样会导致同一用户和 Agent 的多个前端聊天条目可能共享同一个 backendSessionId。

如果请求直接带了非空 sessionId，ChatService 当前不会校验它是否属于该用户与 Agent。Runner 也只检查 ID 非空。

更关键的是，Agent 每次调用模型时重新构造：

    system instruction + 当前 user message

后端没有按 sessionId 查询历史消息并追加到模型输入，所以 sessionId 的存在不代表模型拥有对话记忆。

### 11.2 前端本地聊天

前端另有浏览器本地 session.id，使用 localStorage 保存：

- 消息列表；
- backendSessionId；
- 当前 drawIoXml；
- 标题和最后修改时间。

这是浏览器持久化。换浏览器、清理存储或服务端重启后，两端状态并不自动一致。

### 11.3 已经存在的画布上下文

开启“使用画布上下文”时，前端先从 Draw.io 导出当前 XML，然后把它拼进本次 API message：

    [Context: Current Draw.io XML]
    当前完整 XML
    用户本次修改要求

这已经是一种明确的工作上下文传递，适合“在现有图上增加缓存”这类请求。它仍不等于后端 Memory，因为是否携带由前端按钮决定，后端不存历史，也没有上下文长度预算和版本选择。

## 12. MySQL、Redis 与当前启动的关系

application.yaml 配置了 MySQL 和 Redis，代码也提供 OpenMySQL、OpenRedis，deployments/docker-compose.yml 可以启动两种服务。

但是当前 bootstrap.Build 没有调用这两个函数。真正使用的是：

- ports.NewInMemoryAgentRegistry；
- ports.NewInMemorySessionStore。

所以正常启动当前主链路并不要求 MySQL/Redis 在线。以后 S13 做持久化时，“使用现有 MySQL 技术栈”表示把已有 GORM 适配器正式接入 Bootstrap 和 Repository，不表示项目现在已经把聊天、Session 或图纸写进数据库。

## 13. ADK、Eino 与自定义运行时怎样表述

go.mod 包含 google.golang.org/adk。当前代码用它创建 loggingplugin.Plugin，再包装成项目自己的 RunnerPlugin。但适配器只是检查 callback 是否存在并打印日志，没有调用 ADK callback 的原始执行逻辑。

核心 Agent、Workflow、Runner、SessionStore、ToolRouter 和 OpenAI 客户端都是本项目代码。

面试时可以说：

> 项目采用端口与适配器方式实现了自定义 Agent 运行时，并对 Google ADK logging plugin 做了有限适配；模型调用走自定义 OpenAI-compatible 客户端。

不要直接说“整个工作流由 Google ADK/Eino 执行”，因为代码证据不支持这个范围。

## 15. 这次纠正了哪些旧描述

| 原描述 | 问题 | 现在的准确表述 |
|---|---|---|
| Reviewer 只按提示词返回 XML | 容易让人理解为 Reviewer 只负责格式输出、不负责修正 | Reviewer 被明确要求检查并直接修正，最后输出完整 XML；缺的是程序可见的审查状态和确定性门禁 |
| 原后端相信 Reviewer 返回的字符串 | 方向对，但缺少“Reviewer 本来就是 XML 协议”的上下文 | Runner 知道最后结果应当是 XML，却没有验证实际 string 是否满足 XML/Draw.io 契约 |
| 项目没有 Streaming | 不准确 | 已有单模型 token 流和 /chat_stream；缺的是 Workflow 阶段事件和前端消费 |
| 项目没有 MCP | 不准确 | 已有 SSE MCP 协议客户端；当前有服务可用性、静默降级、Schema 丢失和 Skill 执行缺口 |
| MySQL/Redis 是当前运行依赖 | 不准确 | 有配置与适配器，但 Bootstrap 未接入，当前会话与 Registry 都在内存 |
| 当前目录没有 .git | 已过期 | 现在已有 Git；原项目行为基线仍以 Day 1 的 75 文件快照为准 |
| 某次 404/EOF/429 说明项目不能运行 | 推断过度 | 只表示当时凭据、网关、上游或网络状态；用户已确认项目此前正常运行 |
